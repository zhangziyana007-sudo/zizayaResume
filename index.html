我的 Vibe Coding 感悟

关于 Vibe Coding

在这个过程中，最核心的是 Know-how：知道目标是什么，知道流程怎么拆，知道系统应该怎么闭环。相比传统开发更强调手写实现细节，Vibe Coding 更考验妙手偶得的点子、架构技术的判断和问题拆解能力。代码实现当然仍然重要，但它不再是唯一瓶颈。

关于 Agent

我理解 Agent 本质上是“人通过模型操作电脑”的桥梁。无论是最近比较火的 OpenClaw、Hermes，还是各种 AI 编程与自动化工具，本质上都是在这个桥梁上增加更多和电脑沟通、执行任务、调用工具的方式。

这有点像 Windows 系统曾经为普通人提供了可视化操作电脑的入口。Agent 要真正产生价值，也需要把复杂能力收束成更简洁、更可视化、更接近商业场景的工作流系统。

对于最近热门的 harness 架构，我的理解是：Know-how + Agent。智能体最终有价值的形态，不只是会聊天，而是能承载一套真正可执行、可复用、有商业价值的 Know-how 工作流。

关于 Skill

Skill 的出现，本质上是在某个精细领域里沉淀一套 Know-how。但我认为很多开源项目对 Skill 有一个误区：喜欢追求“一个 Skill 解决所有问题”。

凡是功能越全、提示词越冗杂、约束越复杂的 Skill，实际效果往往越差。因为它把不确定性都塞给了模型且占用了更多的上下文，反而降低了工作流稳定性。

我更认可的 Skill 设计是：

  • 固化一套清晰的生产流程。
  • 把繁琐、可重复、可脚本化的任务封装起来。
  • 把真正需要判断、表达和创造的部分交给 AI。
  • 让提示词在流程里起润滑剂和创造作用，而不是制造新的不确定性。

一个 Skill 只做好一件事或一类事，往往更稳定，也更容易被 AI 和人反复调用。

关于面向 AI 编程

在用 AI 开发各种小工具的过程中，我发现很多人都会遇到一个问题：工具越做越多，但使用频率越来越低。

复杂工具如果没有给 AI 留出调用入口，下一次 AI 想复用它时，可能又要重新写脚本、重新试错，浪费大量上下文和 token。因此我越来越认同“面向 AI 编程”的思路：开发工具时，不只考虑人怎么点，也要考虑 AI 怎么调用。

这意味着工具最好保留 API、CLI 或结构化输入输出，让 AI 能够稳定调用，而不是只能服务一次性的人工操作。

代表作品

AINewsSkill｜AI 早报自动化生产系统

作品链接：https://github.com/zhangziyana007-sudo/AINewsSkill

一句话：这是我最新开发的 AI 日报图文项目，也是我最近对 Vibe Coding、Agent、Skill 和内容自动化理解的一次实践。

起初做这个项目，是因为我读到一个观点：Markdown 给 AI 看，HTML 给人看。 这个说法虽然被调侃为“快来帮帮我们，token 滞销了”，但它给了我新的启发：AI 内容生产不应该只停留在生成一段文字，而应该变成一条可复用的生产链路。

这个项目围绕 AI 早报生产，把搜索、生成、排版、截图、推送、API 发布和定时运行串成了一条完整流程。

我在项目里做了：

  • 使用 Tavily 获取当天 AI 相关新闻源或是接入卡兹克老师的aibot的api。
  • 使用 DeepSeek 生成结构化日报内容。
  • 用固定 HTML/CSS 模板承载内容，避免 AI 生图的随机性。
  • 用 Playwright 自动截图，生成适合传播的图文内容。
  • 接入飞书机器人推送。
  • 设计适配 Agent / Skill 的 CLI 调用方式，让 AI 调用更加顺手。
  • 生成后端 JSON API，方便后续网页、桌面应用或其他前端集成。
  • 支持 GitHub Actions、VPS cron 或 Agent 定时任务等多种运行方式。

这个项目虽然整体不复杂，但它体现了我对 AI 工具开发的几个判断：

  1. AI 生图即使给出 JSON 和固定提示词，也依然有高随机性；在稳定内容生产场景里，固定 HTML 模板往往更可靠。
  2. Skill 的设计不是越大越好，而是越清晰越好，一个 Skill 只做好一件事或一类事。
  3. 工具要考虑面向AI 调用设计，CLI 和 API 比单纯图形界面更适合进入 Agent 工作流。

如此考虑一个最小实现的项目可以像拼积木一般哪里需要搬哪里，可扩展性大大增加。
